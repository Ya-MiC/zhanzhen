## 1. 支持的版本

| 版本 | 支持状态 |
|------|----------|
| 0.1.x | ✅ 接收安全修复 |
| < 0.1.0 | ❌ 不存在（首个公开版本即 0.1.0） |

预发布版（v0.2.0-alpha 起）按 SemVer 处理，安全问题同样受理，但修复随下一个正式版发布。

## 2. 漏洞报告渠道

**请勿在公开 Issue / PR / 讨论区披露安全细节。**

- 首选：GitHub 私有漏洞报告——仓库页 → Security → Report a vulnerability
  （Private vulnerability reporting）。这是当前唯一官方渠道：项目早期没有专职安全邮箱，
  用平台私密通道比公开渠道更可控，也留下完整时间线。
- 报告内容请包含：受影响版本/提交哈希、复现步骤或 PoC、影响评估、修复建议（如有）。
- 收到后我们会在响应时限内（§3）通过 GitHub 平台回复确认，并保持单线沟通直到披露。

**Safe Harbor**：以善意研究为目的、仅影响自有实例、不触碰他人数据、报告前不公开细节的
安全测试，我们不会对其采取法律行动，并会在致谢中署名（除非你要求匿名）。

## 3. 响应时限承诺

| 阶段 | 时限 |
|------|------|
| 确认收到 | ≤ 72 小时 |
| 初步评估定级（CVSS v3.1 口径内部评估） | ≤ 7 天 |
| 高危（CVSS ≥ 9）/ 可远程利用且无需鉴权 | ≤ 30 天修复或发布缓解措施 |
| 中低危 | 随下一个次版本修复 |
| 协调披露 | 与报告者约定日期，默认修复发布后 90 天内公开 |

项目处于 MVP 阶段，人力有限——时限是承诺也是诚实的上限；若延期会主动向报告者说明进度。

### 3.1 严重度定级参照

| 级别 | 典型情形（结合本产品形态） |
|------|----------------------------|
| 高危 | 无需鉴权读取任意租户账套/原始凭证；事件链校验被绕过；确认分录被静默改写 |
| 中危 | 需本机访问权的提权/越权；错误信封泄漏敏感路径或内部结构 |
| 低危 | 缺少纵深防御项（如缺失安全响应头）；文档误导导致的不安全部署 |

## 4. 威胁模型速览

| 资产 | 主要威胁 | 现状缓解 | 残余风险 |
|------|----------|----------|----------|
| 原始凭证文件 | 替换/篡改后抵赖 | 入库即服务端重算 SHA-256，对象只读 | 宿主机文件系统权限失控 |
| 事件链与快照 | 事后改账、删除痕迹 | append-only + 同聚合哈希链 + verify_chain | 攻击者拿到宿主机可整体替换快照并重建链——链证明的是「自此之后未改」，不是「最初为真」，务必保管好备份 |
| 分录数据 | 确认后暗改 | JOURNAL_CONFIRMED 不可变，只能红字冲销 | 同上 |
| AI 通道 | 数据外泄、注入 | 默认关闭；只喂已确认结构化字段；输出 schema 校验 | 见 §7 专项分析 |
| API Key | 泄漏滥用 | 仅环境变量注入，不入库不留痕 | 使用者配置不当（如写进 shell 历史） |

## 5. 安全基线（已实现）

来自代码事实，逐条可在源码验证：

- **证据完整性**：原始文件入库即由服务端重算 SHA-256（不信客户端）；文件对象按哈希寻址只读；
- **事件防篡改**：append-only 事件日志 + 同聚合哈希链 + `verify_chain()` 全链校验；
  快照损坏时拒绝静默清空、保留现场抛错；
- **账务不可变**：分录确认后不可 UPDATE/DELETE，纠错只能生成关联的红字冲销；
  `lines_hash` 锁定确认时刻的行内容；
- **状态机防线**：非法迁移一律拒绝并落事件（如未覆核不得做账、已确认不得回退草稿）；
- **错误面收敛**：统一信封 `{code, message, details, trace_id}`，不回传堆栈；
  日志不落凭证正文；
- **AI 默认关闭**：三个 `ZZ_AI_*` 变量齐备才启用；输出强制 schema 校验、无写数据通道；
  每次调用留痕（prompt 版本/模型/响应哈希）。

## 6. 已知缺口（诚实清单，部署前必读）

以下为 v0.1.0 明确不提供的能力（详见 LIMITATIONS.md），**不是漏洞而是边界**，
但直接决定部署形态：

| # | 缺口 | 部署含义 |
|---|------|----------|
| 1 | 无登录/RBAC/会话管理 | 任何能访问端口的人都是全权用户。只允许本机（默认绑 127.0.0.1）或放在 VPN/反代+SSO 之后 |
| 2 | 单租户目录级隔离 | 不同客户数据必须不同数据目录+不同进程，严禁共用一个实例 |
| 3 | 快照为明文 JSON | 目录权限收紧到运行账户（700/600）；备份加密存储 |
| 4 | 并发写入未加锁 | 单实例单操作者使用，双开可能互覆快照 |
| 5 | Docker 映射绑定 0.0.0.0 | compose 默认对局域网开放——加防火墙规则或改绑 127.0.0.1:8710:8710 |
| 6 | 不做发票联网验真 | 真伪核验走官方线下渠道，程序结果不含真伪结论 |

## 6b. 部署加固检查清单

- [ ] 服务仅绑 127.0.0.1，或置于反代（Nginx/Caddy 终止 TLS）+ 访问控制之后
- [ ] 对外绝不裸暴露 8710；云上安全组只放行必要来源 IP
- [ ] `ZZ_DATA_DIR` 位于非公网同步目录；权限 700，快照 600
- [ ] `.env` 含 `ZZ_AI_API_KEY` 时不入库、不进镜像构建参数（compose 的 `env_file` 属运行时注入）
- [ ] AI Key 定期轮换；泄露立即在服务商侧吊销
- [ ] 以非 root 运行容器/进程
- [ ] 定期 `zhanzhen verify` 校验链完整性并留存校验输出作为底稿附件
- [ ] 升级跟进 Release 页；升级前整目录备份数据

## 7. AI 助手专项安全分析

- **出网面**：仅当你配置了端点才存在；目的地是你填写的 `ZZ_AI_BASE_URL`，程序无硬编码服务商。
- **注入面评估**：进入 prompt 的 findings 解释文本由规则引擎程序化生成（固定模板拼接），
  不是用户自由文本，注入面很小；但对手方名称等 OCR 字段来自外部世界——它们以 JSON 数据
  形式拼入请求，若你使用的端点/模型把数据当指令执行，理论上存在间接注入。缓解：助手输出
  只作展示建议、无工具调用能力、无任何回写通道，最坏后果是「一段建议文本不可信」。
- **留痕与审计**：每次调用的模型名、provider 主机名、响应哈希、schema 校验结果入
  model_runs（当前为进程内存，重启清空——落盘持久化在路线图）。

## 8. 密钥与敏感信息管理

- 全部配置经环境变量注入（CONFIG.md §1），仓库内不存在也不应存在任何真实密钥；
- 提交前自查：`git log -p` 抽查疑似 Key 字样；CI 侧后续接入 secret 扫描（路线图项）；
- model_runs 留痕记录 provider 主机名与响应哈希，**不含 API Key**；
- 用户数据不属于密钥但同等对待：导出物（report.html / xlsx / csv）含完整业务数据，
  外发前自行脱敏定密。

## 9. 依赖供应链

核心运行依赖刻意最小（pydantic、PyYAML），可选依赖全部 MIT/Apache/BSD 兼容
（兼容性矩阵见 ASSETS_AND_LICENSE.md §5）。当前未启用自动依赖扫描与 lockfile：
升级依赖属显式行为，进 PR 走 CONTRIBUTING.md 流程；引入任何新依赖触发 ADR（条件见该文 §6）。

## 10. 日志与 trace_id 规范

- 服务端每类错误返回 `trace_id`（12 位随机短 ID）；用户报障时附上它即可让维护者把
  Web 弹窗、服务端 stdout 日志、你当时的操作三者对上号；
- 日志内容承诺：不含凭证正文、不含密钥、不含堆栈——只有时间、路由、错误码与 trace_id；
- 因此**不要**把业务数据贴进公开 Issue：先看信封里的 `code` 是否已能定位
  （常见码：`audit_error` / `invalid_state_transition` / `ai_disabled_or_invalid`）。

## 11. 备份与恢复的安全要求

- 备份介质与生产同等对待：含全部账套明文，外置硬盘/U 盘需加密（LUKS/BitLocker 至少其一）；
- 恢复演练建议每季度一次：从备份恢复快照后跑 `zhanzhen verify`，✔ 才算备份有效；
- 备份保留策略示例：日备 7 份 + 月备 12 份轮换；销毁旧备份时连同导出物一起清理，
  避免「主库删了、备份还在网盘里」的隐私残留。

## 12. 事件响应流程（维护者内部口径）

1. 接报 → 72h 内确认并建私密安全 Issue（GitHub advisory 草稿）；
2. 复现 → 定级（§3.1 表）→ 决定 hotfix 或随下版；
3. 修复 PR 标注 `security` 不公开细节，合并后发版并在 Release 说明致谢（经报告者同意）；
4. 90 天协调期结束公开 advisory 全文；每季度复盘时限达成率并入 LIMITATIONS 诚实清单。
