## 0. 使用方法

- 出发拍摄前过一遍 §1；每次打包上传过一遍 §2–§3；收包后在工作台过 §4。
- 任何一项 ✗ 都先按 §5 处置表处理再继续，不要带病往下走——后面每一步都以「证据可信」为前提。

---

## 1. 拍摄前检查（一次性环境准备）

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1.1 | 工作台可达 | 浏览器能打开 `http://<工作台IP>:8710`，右上角「事件链 ✔ 完整」 |
| 1.2 | 手机与工作台网络互通 | 同一内网/VPN；免费版无云端中转，直连工作台 |
| 1.3 | 工作台暴露面安全 | 服务未直接暴露公网（MVP 无登录）；必要时经反代+鉴权 |
| 1.4 | 存储余量 | 手机本地队列预留 ≥ 拍摄张数 × 5 MB |
| 1.5 | 时间准确 | 手机系统时间正确（`captured_at` 会进入采集包元数据） |
| 1.6 | 数据目录就绪 | 工作台 `ZZ_DATA_DIR` 磁盘余量 ≥ 预期包体 × 2 |

## 2. 单张拍摄检查（每张凭证）

| # | 检查项 | 为什么 |
|---|--------|--------|
| 2.1 | 四角完整、无边框遮挡 | 缺角会导致金额区丢失，OCR 只能诚实留空 |
| 2.2 | 光线均匀无反光 | 反光区域识别率骤降，置信度低于阈值会全部转人工 |
| 2.3 | 文字对焦清晰 | 模糊件走三级降级链也救不回来 |
| 2.4 | 一张照片一张凭证 | 多联拼拍会让字段归一化错位 |
| 2.5 | 章印不压关键数字 | 印章覆盖金额/税号时人工覆核成本翻倍 |
| 2.6 | 当场核对本地哈希入队成功 | 队列应有该张的 uuid + sha256 + 时间戳记录 |

> 提醒：v0.1.0 工作台只做 PDF 文本层提取；**图片识别能力在移动端侧链路**
> （系统级 OCR → PaddleLite），服务端高精度 OCR 属专业版规划。端侧识别失败的照片
> 仍应入包——工作台会入库留证并标记待处理，而不是丢弃。

## 3. 打包与传输检查

| # | 检查项 | 说明 |
|---|--------|------|
| 3.1 | 包文件名 | `zhanzhen-capture-<timestamp>.json`，单包 < 50 MB（超限拆包） |
| 3.2 | 包结构顶层含 `items[]` | 工作台按 items 数组逐张收包 |
| 3.3 | 每项必填 `filename` / `content_b64` / `captured_at` | **字段名以当前 API 为准是 `content_b64`**（设计稿历史写法 `content_base64` 已被实现取代） |
| 3.4 | 可选 `note` 备注带上业务语境 | 如「3 月餐费」，导入后显示在收包结果里便于核对 |
| 3.5 | base64 编码完整 | 截断的 base64 解码失败或哈希不符会被拒 |
| 3.6 | 上传前本地预览逐张勾选 | 删除误拍/重复照片后再传——隐私承诺之一（见 MOBILE_WORKFLOW.md §4） |

### 3b. 批量作业策略（>10 张）

| 张数 | 建议做法 |
|------|----------|
| ≤ 10 张 | 单包一次上传，收包后逐张 OCR |
| 11–50 张 | 按业务日/客户拆成多个小包；每包收完核对数量再拍下一批 |
| > 50 张 | 分多天/多时段上传；避免单次作业会话过长导致中途断网后难以对账 |
| 混合类型 | 同包内尽量同凭证类别（发票一包、回单一包），便于收包后批量覆核 |

最小可用包样例（可直接作为自测夹具）：

```json
{
  "version": "1.0",
  "exported_at": "2026-08-25T10:30:00+08:00",
  "app": "zhanzhen-capture",
  "items": [
    {
      "file_id": "vou_01JXEXAMPLE",
      "filename": "vou_01JXEXAMPLE_page1.jpg",
      "mime_type": "image/jpeg",
      "captured_at": "2026-08-25T10:28:12+08:00",
      "content_b64": "<照片的 base64 全文>",
      "note": "3月办公室租金"
    }
  ]
}
```

curl 自测（不经 App 直接验证工作台收包通道）：

```bash
python - <<'PY'
import base64, json, urllib.request
raw = open("p1.jpg", "rb").read()
body = {"items": [{"filename": "p1.jpg", "content_b64":
        base64.b64encode(raw).decode(),
        "captured_at": "2026-08-25T10:28:12+08:00", "note": "自测"}]}
req = urllib.request.Request("http://127.0.0.1:8710/v1/vouchers/capture-batch",
      data=json.dumps(body).encode(), headers={"Content-Type": "application/json"})
print(urllib.request.urlopen(req).read().decode())
PY
```

## 4. 工作台收包后检查

| # | 检查项 | 在哪里看 | 不通过的后果 |
|---|--------|----------|--------------|
| 4.1 | 弹窗「已收入 N 张」= 包内张数 | 收包提示 | 少收→查 §5 HASH_MISMATCH / 解码失败 |
| 4.2 | 凭证箱列表出现 N 行新记录，来源为手机通道 | 凭证箱 | — |
| 4.3 | 每行证据哈希已由**服务端重算** | 列表末列 SHA 前 12 位 | 客户端哈希仅参考，服务端重算不一致即拒收 |
| 4.4 | 逐张点「OCR识别」（或等批量队列） | 凭证箱操作列 | 未 OCR 无法进入覆核 |
| 4.5 | NEEDS_REVIEW 凭证全部完成人工覆核 | 覆核页签 | 不能生成分录（质量门拦截） |
| 4.6 | 分录确认后事件链仍 ✔ 完整 | 页头指示器 / `zhanzhen verify` | 变红立即停止并排查 |
| 4.7 | 手机本地队列对应项标记已上传 | App 队列页 | 避免「待同步」徽章长期悬挂造成重复导出 |

## 5. 故障处置速查

| 现象 | 可能原因 | 处置 |
|------|----------|------|
| 导入弹「不是湛箴采集包」 | JSON 顶层缺 `app: zhanzhen-capture` 标识或文件损坏 | 用模板重打包；校验 JSON 可解析 |
| 收包数量少于包内张数 | 个别项 base64 截断/解码失败 | 定位失败项重新拍照补包；已收部分不受影响 |
| 服务端报哈希校验失败 | 传输中被改写 | 重拍该张（对应错误码 `HASH_MISMATCH`） |
| OCR 后大量 NEEDS_REVIEW | 端侧置信度低/版面复杂 | 正常兜底路径：逐张人工覆核；持续过低则改善拍摄条件 |
| 工作台不可达 | 断网/服务停机 | 对应 `SERVER_UNAVAILABLE`：数据留在手机本地队列，恢复后重传，勿重复建包 |
| 上传中断 | 弱网 | 大包拆小分批传；已入库凭证不会因后续失败回滚 |

错误码语义表（`QUOTA_EXCEEDED` / `TENANT_FROZEN` 等）以 [MOBILE_WORKFLOW.md](MOBILE_WORKFLOW.md) §6 为权威源。

## 6. 安全与隐私红线（拍摄环节专属）

- [ ] 工作台地址不外发给无关人员（单机 MVP 无登录）
- [ ] 采集包不上传到任何第三方网盘中转
- [ ] GPS 仅在用户显式开启时记录；默认关
- [ ] 上传完成后及时清理手机本地已同步照片
- [ ] 含真实客户数据的采集包，用完即从「下载文件夹/聊天工具」删除

完整的数据出网边界见 [PRIVACY.md](biz/PRIVACY.md)；执业保密义务视角的红线见
[CPA_COMPLIANCE.md](biz/CPA_COMPLIANCE.md)。
